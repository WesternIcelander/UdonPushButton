# 8.10 Hold to keep the button pressed, with a release action

## What was done

- **ClientSim check first:** ClientSim's `ClientSimPlayerRaycaster.UseInput` only interacts on use-down (`if (!value) return;`), and the use-up reaches Udon separately as `InputUse(false)` through `UdonManager.RunInputAction`. So `Interact` fires on input down and holding works this way.
- `PushButton`:
  - **Holding a click.** New `clickHeld`, set by `StartClickAnimation`. `UpdateClickPress` keeps the click at the bottom while `clickHeld`, and only ends it (`clickActive = false`) once it's released after the press-in. A tap released early finishes pressing in, holds the bottom for one frame, then springs back as before.
  - `InputUse(bool value, UdonInputEventArgs args)` returns straight away unless it's a use-up and this button holds a local click. Otherwise it clears `clickHeld`, sends `NetReleaseClick` to Others, and fires the release action if the press has fired. The manager isn't involved.
  - **Remote viewers.** `NetPlayClickAnimation` records the presser's player ID from `NetworkCalling.CallingPlayer` (`clickPresserId`, -1 if there's none) and holds too. `NetReleaseClick` releases the hold only when its sender is that presser, so one player's release can't cut short another player's later hold. `OnPlayerLeft` releases a remote hold whose presser leaves. A local click that's held now also blocks incoming networked clicks, as one still pressing in did before.
  - **Release action.** New `releaseEventName` in `Action`, under `eventName` (empty by default), sent to `targetBehaviour` by `FireRelease()`. A null or empty name, or no target, sends nothing and doesn't warn. `releasePending` is set once a press has fired. The release fires at the first of these: the click's use-up (`InputUse`); re-arming in `UpdateTrigger` (fingertips); or `ResetToRest` (button disabled, manager disabled, out of range), where it fires last, once the button is already at rest. If the press action itself resets the button (spotted by a `resetCount` that `ResetToRest` bumps), the release fires straight after the press action instead of inside it. `UpdateTrigger` now returns whether it ran either action, so the tick stops when the release action disables the button or the manager, just as it does after the press action.
- `PushButtonEditor`: `releaseEventName` uses the same event dropdown as `eventName`, with a "(none)" choice that leaves it empty.
- `ButtonActionExample`: a new `OnButtonReleased` that logs `[ButtonActionExample] released by …`. The scene button's `releaseEventName` stays empty.
- Tests:
  - New `AddHoldTest` (`PushButtonPlayModeTests.Hold.cs`), run after the VR trigger test.
  - New helpers: `ReleaseUse()` sends `InputUse(false)` the way ClientSim does (`UdonManager.Instance.RunInputAction(UDON_INPUT_USE, …)`). `ClientSimInputManager.GetInput()` isn't reachable from the tests. `AsCaller(player, action)` runs a call inside `NetworkCalling.WithNetworkCallingContext` (by reflection), so `CallingPlayer` is that player. `Tap`, `TapWithHelper` and `NetTap` are a quick click and a quick networked click (both events).
  - `SetUpActionTarget` now also points `releaseEventName` at `OnButtonReleased`, and counts release logs (`releaseCount`) and the order of press and release logs (`actionOrder`).
  - Existing tests used clicks that never released, so they now use `Tap` / `TapWithHelper` / `NetTap`. The VR trigger test expects `NetReleaseClick` after each of its clicks. The inspector test expects the example's two events, and `NetReleaseClick` in the button's own events (`InputUse` and `OnPlayerLeft` left out). It also checks that `releaseEventName` comes right after `eventName` under `Action`, and that the scene button leaves it empty.

## How it was checked

- `refresh` + `Re-compile All Program Sources`: UdonSharp compiled 11 scripts with no errors.
- `AddHoldTest`:
  - **Held click:** a click held for 1 s stays at the bottom, fires the press once, and sends only `NetPlayClickAnimation`. On the use-up it fires the release once (after the press) and sends `NetReleaseClick`, then springs back. A further use-up does nothing.
  - **Quick tap:** with a 0.5 s press-in, the button is still pressing in after the input is released. It then fires press then release once each and ends at rest.
  - **Remote presser:**
    - a remote player's networked click records them as the presser and holds at the bottom;
    - releases from the local player, from no sender, and the local use-up are all ignored;
    - the presser's `NetReleaseClick` ends the hold and the button springs back;
    - a release 0.1 s into a 1 s press-in lets the press-in finish (checked part-way), then the button springs back at `returnSpeed`;
    - the presser leaving (`ClientSimMain.RemovePlayer`) ends a hold;
    - none of this ever fires the press or the release locally.
  - **Fingertip:** pressing to the bottom fires the press. Wobbling at 0.75, 0.6 and 0.95 of travel doesn't release. Going to 0.3 releases once, after the press, and nothing more happens on the way out.
  - **Unset release event:** a null and an empty `releaseEventName` each still fire the press, send no release, log no error, and leave nothing pending.
  - **Reset mid-hold:** turning off the button's GameObject during a held click, and separately the manager's UdonBehaviour, fires the release once and leaves the button at rest and cleared. After turning it back on, the late use-up doesn't release again.
  - **VR trigger:** with the local player faked as VR and `allowVRTrigger` on, a trigger hold stays at the bottom, fires the press, and fires the release on the use-up.
  - No errors were logged during the test.
- Full Play Mode suite: 1543 passed, 0 failed, 0 errors logged. Edit Mode build-check tests: 114 passed, 0 failed.
