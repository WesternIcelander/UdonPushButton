# 8.9 Let VR players click with the trigger (optional)

## What was done

- `PushButtonManager`: the `Desktop` header is now `Click`, holding `clickPressDuration` and the new `allowVRTrigger` (default false). `PushSettings` writes `allowVRTrigger` into the button with the other settings, then calls the button's `_UpdateInteractive()`, so every registration and every `ApplySettings()` re-applies the interactive state.
- `PushButton`:
  - `[NonSerialized] public bool allowVRTrigger`, the manager's copy.
  - `SetUpLocalInput` keeps the collider-as-trigger part and calls the new public `_UpdateInteractive()`. That re-reads `IsUserInVR` into `localIsVR` (so it follows the 5.4 test hook too) and sets `DisableInteractive` when there's no manager or the local player is in VR without `allowVRTrigger`; otherwise it enables Interact with `InteractionText = interactText`. `Initialize` no longer sets `DisableInteractive` itself for a missing manager.
  - `Interact()` returns early unless the button is live, Interact is enabled (`DisableInteractive` false), and the local press is 0. The local press covers the local player's own fingertips and the debug fingertip, never remote ones. A trigger click is otherwise exactly a desktop click: same animation, network event and action. It plays no haptics, since `PlayPressHaptics` only runs when the fingertip press reached the bottom.
  - `interactText` moved to the top of the `Action` group, above `targetBehaviour`, and the `Desktop` header is gone. The custom inspector draws the fields in declaration order, so its code didn't need to change.
- Tests:
  - New `AddVRTriggerTest` (`PushButtonPlayModeTests.VRTrigger.cs`), run after the haptics test.
  - New ClientSim hook `StartRecordingNetworkEvents` / `CheckNetworkEvents` records the network events sent. It adds itself to `NetworkCalling.SendCustomNetworkEventProxy`, a static property that's not public outside ClientSim, by reflection, next to ClientSim's own handler (which drops `Others` events). It's removed when Play Mode ends.
  - `allowVRTrigger` is in the settings test's `SettingNames` (test value true), so `ApplySettings`, re-enabling and scene load cover it too.
  - Fixed test leaks the new behaviour exposed. The fingertip test used to leave the local player faked as VR, and its `SetSetting` calls then disabled Interact, which broke the click tests. It now ends back on desktop and calls the new `ApplySettingsNow()`. The player-tracking test had relied on that leak, so it now fakes VR for itself. The haptics test also re-applies the settings after it clears VR.

## How it was checked

- `refresh` + `Re-compile All Program Sources`: no C# errors, and UdonSharp compiled 11 scripts.
- `AddVRTriggerTest`, with the local player faked as VR:
  - setting off: `localIsVR` true, not interactive, ClientSim can't interact, and `Interact()` starts no click, sends no network event and doesn't fire;
  - setting on: interactive with `interactText`, and a ClientSim interact starts a local click, animates in, fires once, plays no haptics, returns to rest and sends exactly one `Others NetPlayClickAnimation`;
  - the debug fingertip holding the button half-way in: `Interact()` is ignored, with no click, no network event and no fire;
  - a remote VR finger holding it half-way in (the local player 1.5 m aside): `Interact()` clicks, sends the network event and fires;
  - `ApplySettings` flips `DisableInteractive` off and on;
  - on desktop, it stays interactive with the setting off and on;
  - the manager's `allowVRTrigger` and `clickPressDuration` sit under `Click`.
- Inspector test: `interactText` is shown just before `targetBehaviour` under the `Action` header, and no `PushButton` field has a `Desktop` header.
- Full Play Mode suite: 1451 passed, 0 failed, 0 errors logged. Edit Mode build-check tests: 114 passed, 0 failed.
- Left for 9.3/9.4: a real VR trigger click in a built world.
