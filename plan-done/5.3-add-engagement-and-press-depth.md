# 5.3 Add engagement and press depth

`Update` now calls `UpdateFingertipPresses()` right after rebuilding the rest pose. It loops over `trackedPlayers`, runs `GetFingertips` for each one, and evaluates every valid slot. The local player's slots (`player.isLocal`) feed `localPress` and everyone else's feed `remotePress`, taking the deepest engaged press. Slots that are invalid (finger turned off, bones missing, player invalid) have their state cleared. `debugFingertip` is evaluated with the unscaled `fingertipRadius` and its own state (`debugEngaged` / `debugWasInFront`), and adds to `localPress`. `EvaluateFingertip(toRest, tip, radius)` does the [Fingertip engagement](../PLAN.md#fingertip-engagement) rules. UdonSharp has no `ref`, so it passes state through the `tipEngaged` / `tipWasInFront` fields. It computes `press = Dot(p, pressAxis) + frontFaceOffset + radius` (2.2's sign convention) and an `inFootprint` test that grows the footprint by the radius. "Past the face" means `press > 0`. A tip engages if it was in front last frame (in the footprint, `press <= 0`) and is now in the footprint and past the face. It stays engaged while in the footprint and past the face. It returns `clamp(press, 0, travelDistance)` when engaged, otherwise 0. `debugLocalPress` and the 5.2 hook in `Update` are gone. `GetFingertips` still leaves the last evaluated player's tips in the buffers, which the 5.2 test reads while the local player is alone. **Harness:** `SetLocalPress` now drives a test fingertip object (`PlaceDebugTip(press, u, v)` places it in the rest frame; fraction 0 puts it 1 cm in front of the face). The press tests start the tip in front before pushing. The trigger test's direct `remotePress` poke was dropped, because `Update` now overwrites it each frame. New `AddEngagementTest` (debug fingertip, unrotated): in front → half-way (press 0.0095, no fire) → 0.03 m in (stops at 0.0190, fires once, no refire while holding) → pulled out (re-armed) → pushed again (fires, 2 total). Side entry, back entry (from 0.1 m behind) and sliding back in after leaving sideways all stay disengaged at press 0. A tip half its radius past the footprint edge still engages. `AddPlayerTrackingTest` now uses a real press, not a hand-set flag: it moves the button so the **local ClientSim avatar's left index fingertip** comes in from the front to half the travel (press 0.0095), and checks that it stays engaged through both joins and both leaves, then releases when the button moves away. New `AddRemotePressTest` spawns a ClientSim remote player, moves the local player 1.5 m aside, and moves the button onto the remote avatar's left index fingertip, first in front and then 0.03 m in. Result: `remotePress` 0.0190, `localPress` 0, button at the stop, no action log, still armed, released once moved away. UdonSharp compiled 10 scripts with no errors. Result: `[PushButtonTest] done: 240 passed, 0 failed`, 0 errors, 0 exceptions (the trigger again only left Play Mode at "time up"). **For 5.4:** with the VR filter, the desktop ClientSim local player won't be evaluated any more. `AddPlayerTrackingTest`'s carry-over check engages the local avatar's real fingertip, so it will need to change, e.g. to engage the remote player's fingertip instead. ClientSim remote players are desktop too (`IsUserInVR` false), so `AddRemotePressTest` will also need a way to count them as VR, or a different check.
